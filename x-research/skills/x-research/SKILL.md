# X (Twitter) Research via xAI Grok API

依頼を受けて **Grok へのプロンプトを書き**、`x_search` サーバーサイドツールで
X を調査させる。取り出すのは 3 点セット:

1. **レポート** — 依頼への回答 (Markdown)
2. **ソースとなる発言** — 各知見を裏付けるポストの原文引用
3. **URL のリスト** — ポストの URL と、ポストが指す論文・リポジトリ等の URL

モデルが出したポスト URL は API が収集した citations と照合され、裏付けの
ないものは引用ごと除去される。API 仕様・料金・検証の仕組みは
`${CLAUDE_PLUGIN_ROOT}/skills/x-research/references/xai-api.md` を参照。

## 前提

- `XAI_API_KEY` が必要。**事前に確認しない** — 未設定ならスクリプトが実行時に
  exit 2 とメッセージを返すので、それを受けてから案内する。Claude Code の
  セッション環境と Bash ツールの環境は一致しないことがあり、事前チェックは
  設定済みのキーを未設定と誤判定する
- 未設定だったときの案内: console.x.ai でキーを作成し (セルフサーブ、サブスク
  不要)、プリペイドクレジットを少額 ($5〜) 手動購入する。invoiced billing limit は
  $0 のまま触らない
- 実行は `uv run` (依存は PEP 723 で自動解決)

## Arguments

- **調査内容**: `$ARGUMENTS` と会話コンテキストから、何を調べたいかを判断する
- **期間**: `--from` / `--to` (`YYYY-MM-DD`)。プロンプト内の「先週」等より
  こちらの指定が確実に効く
- **モデル**: `--model`。**既定の grok-4.3 から勝手に変えない**。
  「丁寧に」「網羅的に」といった要望は `--max-turns` を増やして満たす。
  ユーザーがモデル名 (`grok-4.6` 等) を明示的に指定したときだけ変更し、
  その際は下記「モデルの選択」の注意点とコスト見込みを伝えてから実行する
- **確認スキップ**: `-y` / `--yes`

## Instructions

### 1. Grok へのプロンプトを書く

依頼と会話コンテキストから、Grok に渡す調査指示を組み立てる。Grok はサーバー側で
検索を繰り返すエージェントなので、下調べをせずプロンプトを書くことに集中してよい。

まず依頼の重さを見極める。「ざっと」「最近何を言っているか」のような**軽い依頼に
重いプロンプトを書かない**。特定アカウントの直近ポストを見るだけなら、数行の
プロンプトと `--max-turns 2`、期間指定なしで足りる (直近が自然に上位に来る)。
以下は腰を据えた調査を頼まれたときの組み立て方である。

プロンプトが検索の範囲と深さを決める。キーワードだけを渡さず、以下を含める:

- **調べる対象と目的**: 何を知りたいのか、その情報を何に使うのか。
  「ASR の最新モデルを知りたい (日本語で使えるかを判断したい)」のように
  目的まで書くと、モデルが取捨選択の基準を持てる
- **探索の方針**: 「1 クエリで済ませず、語を変えて複数回検索する」と明示する。
  `mode` は `Top` (反響大) と `Latest` (新着) の両方を回すよう指示すると
  取りこぼしが減る。重要なポストを見つけたらスレッド全体を辿るよう指示する
- **検索クエリの設計**: X の検索演算子はプロンプトに書くとエージェントが
  内部クエリに使う (下記「検索演算子」参照)。**日本語の情報が欲しいなら
  日本語のクエリ語を明示的に列挙する** — 英語クエリでは日本語ポストは拾えない
- **各知見に何を記録させるか**: `detail` に入れる内容を具体的に指示する。
  技術情報なら「手法、対応言語、ベンチマーク数値、公開先」、
  評判調査なら「賛否とその理由、反論の有無」など
- **レポートの構成**: 「時系列で」「モデルごとに表で」「賛否に分けて」など、
  望む形を書く。指定しなければモデルが決める
- **除外条件**: 宣伝ポスト、bot、内容のない再投稿など弾いてほしいものがあれば書く。
  ただし**使用感・評価・不満は除外しない**。「試したら日本語の CER がひどい」
  「実運用でこう詰まった」といった一次評価は公式リリース告知より価値が高いことが
  多く、X を調べる理由そのものである。除外するのは発信者の宣伝と中身のない言及で
  あって、書き手の主観が入っていることではない

プロンプト自体は依頼の言語で書いてよい (日本語の依頼なら日本語で書く)。

**プロンプトに書かないこと**: 出力スキーマの説明 (`report` / `findings` /
`sources` の定義や、引用が verbatim であること) はスクリプト側の system prompt が
既に指示している。重複させない。

#### 検索演算子

`x_keyword_search` の `query` は X advanced search の演算子を解する。プロンプトに
書いた演算子はそのまま内部クエリに渡ることを実測で確認済み (`since:` `until:`
`filter:links` `url:arxiv.org` が発行クエリに現れ、「日本語クエリに `min_faves:`
を付けない」という指示も守られていた)。ただし毎回守られる保証はないため、
外せない制約は演算子ではなく `--from` / `--to` / `--handles` で指定する。

| 用途 | 演算子 |
|------|--------|
| アカウント | `from:` `to:` `@user` `list:` |
| 期間 | `since:` `until:` `within_time:7d` |
| 反響 | `min_faves:N` `min_retweets:N` `min_replies:N` `filter:has_engagement` |
| 種別 | `filter:links` `media` `images` `videos` `news` `replies` `quote` |
| リンク先 | `url:arxiv.org` `url:github.com` |
| 論理 | `"完全一致"` `OR` (大文字) `-除外` `()` |

注意点:

- **`lang:ja` は使えない** (ツールスキーマに存在しない)。言語の制御は
  クエリ語自体を日本語にすることで行う
- `min_likes:` / `min_reposts:` (X API v2 の綴り) ではなく
  **`min_faves:` / `min_retweets:`** を使う
- **日本語クエリに `min_faves:` を付けない**。母数が少なく結果が枯れる
- 1 回の検索の `limit` は既定 3・最大 10 程度。閾値を積み上げると候補が消える
- 期間は演算子より `--from` / `--to` の方が確実。ただし `x_user_search` と
  スレッド取得には効かないため、範囲外のポストが混ざりうる

#### 引用を確実に得る

**明示しない限りモデルは逐語引用をしない** (要約と閲覧数を並べて終わる)。
また X の citation URL は `https://x.com/i/status/<id>` 形式で**ハンドル名を
含まない**ため、誰の発言かはモデルに書かせるしかない。

この 2 つはスクリプト側で要求済みなので、通常はプロンプトに書かなくてよい。
原文の正確さが特に重要な依頼でのみ「原文のまま、翻訳・要約せずに引用する」と
重ねて指示する。

### 2. ユーザーに確認する

実行には課金が伴うため、**何を実行するかは必ず可視化してから走らせる**。
`-y` の有無で変わるのは「応答を待つかどうか」だけである。

コスト見込みは `--max-turns` から出す (grok-4.3)。★ が実測値、他は内挿:

| `--max-turns` | 見込み | 使う場面 |
|---|---|---|
| 2 | $0.4 前後 ★ | 軽い依頼 (特定アカウントの直近を見るだけ) |
| **5 (既定)** | **$0.5-0.8** | **判断がつかないときは常にこれ** |
| 10-12 | $0.8-1.0 ★ | 足りなかったとき、または最初から網羅性を求められたとき |

上位モデルではこのレンジは使えない (「モデルの選択」参照)。

**適切な `--max-turns` は事前には決まらない**。何回検索すれば足りるかは、その話題に
どれだけポストがあるかで決まり、投げてみるまで分からない。したがって**最初から
上限を読み切ろうとせず、既定の 5 で投げて、足りなければ上げて投げ直す**。
足りたかどうかは実行後に分かる (Step 4)。

**`-y` / `--yes` がある場合**: 質問はせず、これから実行する設定とコスト見込みを
1 行提示してから実行する (応答は待たない)。コマンドライン全文ではなく、モデル・
主要オプション・期間が分かる要約でよい。

```
grok-4.3 / --handles AnthropicAI / --max-turns 2 / 期間指定なしで実行します (見込み $0.4 前後)
```

**`-y` がない場合**: 実行の可否は必ず `AskUserQuestion` ツールで問う。「これで
よいですか?」とテキストで書いて止まってはならない (プロンプト本文をテキストで
示すのは可)。依頼の明確さで 2 通りに分かれる。

- **調べる対象と観点の両方が読み取れるとき** (例: 「gpt-realtime の実装知見」
  — 対象=gpt-realtime、観点=実装知見): **プロンプト全文を本文に示してから**、
  `AskUserQuestion` で「このまま実行」「プロンプトを修正」「中止」を選ばせる。
  質問側には設定 (期間・ハンドル・`--max-turns`・コスト見込み) だけを載せる。
  全文を見せずに「修正」を選ばせても、ユーザーは何を直すか判断できない
- **どちらかが読み取れないとき** (例: 「音声 AI の話題」— 対象は広く、観点は
  「話題」で未特定): プロンプトを書く前に、`AskUserQuestion` で求める情報を
  具体化する質問をする。聞くべきことの例: 知りたいのは何か (新規リリースか、
  実装知見か、評判か) / 期間 / 日本語の情報も要るか / 特定のアカウントに
  絞るか / 何に使うのか。答えを得てからプロンプトを書き、上の分岐に合流して
  改めて確認する (`AskUserQuestion` は具体化と実行確認で計 2 回になる)

### 3. 実行する

プロンプトは `Write` ツールでファイルに書き、`--prompt-file` で渡す
(改行や引用符でシェルが壊れるのを避ける)。シェルのヒアドキュメントは使わない。

まず `Write` で Step 1 のプロンプトを書き出す。パスは一時ディレクトリでよい
(例: `/tmp/x-research-prompt.txt`)。次に実行する:

```bash
uv run ${CLAUDE_PLUGIN_ROOT}/skills/x-research/scripts/search.py \
  --prompt-file /tmp/x-research-prompt.txt \
  --from 2026-08-01 --to 2026-09-01 \
  --raw-out /tmp/x-research-raw.json
```

`--raw-out` は常に付ける。Step 4 の検証で生のレスポンスが要る場面があり、
付けても料金は変わらない。

`--max-turns` は既定が 5 なので、既定でよければ書かなくてよい。軽い依頼で 2 に
下げるとき、深掘りで上げるときだけ明示する。ゼロや極端に大きい値は渡さない
(上限なしはサーバー側の上限に任せることになり、課金が読めない)。

| オプション | 用途 |
|-----------|------|
| `--prompt` / `--prompt-file` | 調査指示 (どちらか必須) |
| `--from` / `--to` | 期間 (`YYYY-MM-DD`)。**`--to` は常に「含めたい最終日の翌日」を渡す** (8 月分なら `--to 2026-09-01`)。その日を含まない挙動が実測されており、翌日指定はどちらの挙動でも安全 |
| `--handles` / `--exclude-handles` | 対象/除外アカウント (カンマ区切り、最大 20、併用不可) |
| `--model` | 既定 grok-4.3。下記「モデルの選択」参照 |
| `--max-turns N` | 既定 5。軽い依頼は 2、深掘りは 10-12。足りなければ上げて投げ直す |
| `--effort none\|low\|medium\|high` | reasoning effort。**通常は指定しない** (既定に任せる) |
| `--previous-response-id ID` | 追い質問 (再検索なし)。**出典が付かない** — Step 5 参照 |
| `--retries N` | 5xx / 429 の再試行回数 (既定 2)。API 側の一時的な 500 は実際に起きる |
| `--raw-out FILE` | 生レスポンス保存 |

出力の `search_calls` には、エージェントが実際に投げたクエリが入る。空振りした
ときは、まずここを見てプロンプトに書いた語や演算子が検索に反映されているかを
確認する。

`--handles` は「その人たちの発言だけ」を見るときに使う。ある話題への反応を
調べるときに指定すると、反応している側を除外してしまう。

#### モデルの選択

**既定の grok-4.3 を使う。ユーザーが明示的に指定した場合のみ変える。**

上位モデル (grok-4.5 / 4.6) は検索を深く回す傾向があり、同じ `--max-turns` では
**検索でターン予算を使い切り、レポートを書かずに空の骨組みを返すことがある**。
それでも API は `status: "completed"` を返すため、失敗は `sourcing` の
`finding_count` でしか検出できない。またループの累積入力が膨らむので、コストは
検索回数の増加以上に伸びる。

ユーザーが上位モデルを指定したときは `--max-turns` を大きめに取り、コスト見込みを
伝えてから実行する。実測値は `references/xai-api.md` を参照。

### 4. 検証してから報告する

出力 JSON:

```json
{
  "result": {
    "report": "# 依頼への回答 (Markdown)",
    "findings": [{"point": "...", "detail": "...",
                  "links": ["https://arxiv.org/abs/..."],
                  "sources": [{"url": "https://x.com/...", "author_handle": "...",
                               "date": "2026-08-20", "quote": "投稿の原文"}]}],
    "coverage_note": "何を検索し何を拾えなかったか"
  },
  "citations": {"x": [...], "other": [...]},
  "search_calls": [{"query": "ASR since:2026-08-01 filter:links", "mode": "Top"}],
  "linked_urls": ["..."],
  "dropped_unverified_urls": ["..."],
  "sourcing": {"search_call_count": 4, "x_citation_count": 12,
               "finding_count": 5, "quoted_post_count": 9,
               "unsourced_findings": []}
}
```

報告する前に `sourcing` を見る。

- **`finding_count` が 0 なのに `search_call_count` が 1 以上** → 検索でターン予算を
  使い切り、レポートを書かずに終わっている。`report` が空、または中身のない
  仮置きの文字列になっていないか確認する。API は `status: "completed"` を返すので
  ここでしか気付けない。**検索は課金済み**なので、再実行するなら `--max-turns` を
  上げる
- **`search_call_count` が 0 かつ `x_citation_count` が 0** → 検索せずモデル知識で
  答えている。X の調査結果として提示してはならない。非 X の URL が付いていても
  同じ (X 上の発言の裏付けにならない)
- **`search_call_count` は 1 以上なのに `x_citation_count` が 0** → 検索は走ったが
  citations を回収できていない。結果が捏造とは限らないが、全ソースが検証で
  落ちている。`--raw-out` の生レスポンスを開き、citations / annotations が
  どこに入っているかを確認する (references/xai-api.md の「未検証事項」参照)。
  引用付きの調査結果としては報告できない
- **`unsourced_findings`** → 検証を通った根拠ポストが 1 つもない知見。ツールを
  呼ばずに答えてもスキーマは埋まるため、根拠がなくても自信ありげに残る。
  報告しないか、根拠なしと明示する
- **`quoted_post_count` と `finding_count` の比** → 引用が数件しかないのに知見が
  多い場合、同じポストを使い回している
- **`dropped_unverified_urls`** → モデルが出したが citations になかった URL
  (捏造、または非 X ソース)。その引用ごと除去済み。多い場合は結果全体を疑う
- **`coverage_note` はモデルの自己申告** → 「検索した」と書いてあっても実際に
  検索したとは限らない。`sourcing` の数値の方が信頼できる

**ターン予算が足りたかを判定する**。足りなかったサインは:

- `finding_count` が 0、または `report` が空/仮置き → **明確に不足**
  (スクリプトも警告を出す)
- `coverage_note` が「調べきれていない」旨を述べている
- 依頼が求めた観点のうち、findings が触れていないものがある
- `search_calls` を見て、プロンプトに書いた検索語や演算子がまだ試されていない

いずれかに当てはまったら、`--max-turns` を**倍にして投げ直す**案を用意する
(既定 5 なら 10)。ただし**勝手に投げ直さない**。何が足りなかったかと追加コスト
見込みを示してユーザーに諮る (Step 2 と同じ扱い。`-y` があっても再実行は諮る)。
既に払ったコストは戻らないので、「もう一度同じ額を払う価値があるか」は
ユーザーの判断である。

足りていれば報告に進む。

`sourcing` の数値は普段は表に出さない。ただし再実行を諮るときと、出典に問題が
あって結果をそのまま提示できないときは、判断の根拠として示す。

**報告の形**: `report` を本体として示し、各知見に**発言の引用と投稿リンクを
複数添える**。引用は原文のまま示し (必要なら訳を併記)、`@handle` と日付を添える。
`links` の URL (論文・リポジトリ等) はポストの URL とは別に示す — 技術情報の
調査ではそちらが本命であることが多い。URL の羅列で済ませない。

最後に実費を 1 行添える。**`usage.cost_in_usd_ticks / 1e9` がドル建ての請求額**
(トップレベルの `server_side_tool_usage` は `null` で使えない)。内訳が要るときは
`usage.server_side_tool_usage_details` と `usage.input_tokens` / `output_tokens`。
事前の見積もりはトークン単価から計算せず、実測レンジ (`references/xai-api.md`)
を使う。

### 5. 追い質問

**`--previous-response-id` の結果は出典を検証できない。原則として使わない。**

実測 (grok-4.3): 追い質問は `search_call_count` 0 / `x_citation_count` 0 を返し、
レスポンスに annotations が 1 件も含まれない。モデルは前回の知見を会話状態から
思い出して答えるが、**それを裏付けていた citations は引き継がれない**。結果として
全 findings が `unsourced_findings` に落ち、モデルが書いた URL も検証を通らず
`dropped_unverified_urls` に隔離される。安いが ($0.18)、このプラグインが返すべき
「検証済み出典付きの回答」にはならない。

したがって追い質問も**新規検索で行う** (`--previous-response-id` を付けず、
前回のプロンプトに切り口を足して投げ直す)。ツール課金は乗るが、出典が付く。
新規検索である以上 Step 2 の確認も再度行う (初回と同じ課金が発生する)。

`--previous-response-id` を使ってよいのは、出典が要らない用途に限る
(前回結果の言い換え、翻訳、並べ替えなど)。その場合も結果を X の調査結果として
提示せず、前回レポートの再構成であることを明示する。

### 6. hydrate (必要時のみ)

引用と URL で足りるなら行わない。エンゲージメント数などが必要な場合のみ、
X API (別勘定、$0.005/read) を叩く:

```bash
npx -y @xdevplatform/xurl "/2/tweets?ids=<status_id,...>&tweet.fields=public_metrics,created_at,author_id"
```

## Never

- 結果を悉皆調査・網羅的として提示しない。x_search の recall は保証されず、
  「サンプリングに基づく傾向」でしかない
- `x_citation_count` が 0 の結果を、引用付きの X 調査結果として提示しない
  (検索が走っていた場合は「検証できなかった」と伝える。捏造と断定はしない)
- `unsourced_findings` に載った知見を、根拠があるかのように報告しない
- 引用を書き換えない。原文のまま示す (訳は併記であって置換ではない)
- 知見を引用なしの要約だけで報告しない。何と言われたかが本体である
- citations にない URL を出典として報告しない
- 「N 件中 M 件が肯定的」のような定量的な主張をしない
- `enable_image_understanding` / `enable_video_understanding` を無断で有効にしない
  (トークン課金が静かに膨らむ)

## Examples

```
/x-research ASR の新しいモデルや論文、日本語対応のものを今月分
→ 目的 (日本語で使えるか判断したい)、探索方針 (研究者と公式アカウント、
  英日両方で検索)、記録項目 (手法・対応言語・ベンチマーク・公開先) を
  含むプロンプトを書き、確認してから --from/--to 付きで実行

/x-research gpt-realtime の実装知見 -y
→ 確認をスキップして実行

「@xai の発表を追いたい」
→ --handles xai で発表ポストを列挙するプロンプト。反応を見たいなら
  ハンドル指定なしの別クエリにする

「@OpenAIDevs が最近何て言ってるか、ざっと -y」
→ --handles OpenAIDevs --max-turns 2。期間は指定しない (直近が自然に
  上位に来る)。プロンプトも短くてよい。深掘りより安く済む

「さっきの結果、批判的な意見だけ深掘りして」
→ 前回のプロンプトに「批判的な意見に絞る」を足して新規検索。
  --previous-response-id は出典が付かないので使わない

実行したが coverage_note が「日本語圏は調べきれていない」と言っている
→ 報告と併せて「この観点が拾えていないので --max-turns 10 で投げ直せます
  (追加 $0.8-1.0)」と提示して諮る。黙って投げ直さない
```

上記 1 番目の依頼に対して書くプロンプトの例:

```
X 上で直近 1 か月に共有された ASR (音声認識) の新しいモデル・論文・実装を
調査してください。日本語で実用になるかを判断するのが目的です。

検索の方針:
- 1 クエリで済ませず、語を変えて 6 回以上検索する
- 主要なクエリは Top と Latest の両方で引く
- 英語: "ASR", "speech recognition", "speech-to-text", "multilingual ASR",
  モデル名 (Whisper, Canary, Parakeet 等)。
  filter:links や url:arxiv.org url:huggingface.co を組み合わせた版も試す
- 日本語: 「音声認識」「文字起こし」「ASR」「音声モデル」でも別途検索する
  (英語クエリでは日本語のポストは出てこないため)。日本語のクエリには
  min_faves: を付けない
- 有力なポストを見つけたらスレッドを辿り、続報やベンチマークを拾う

各知見に記録すること: 手法の概要、対応言語 (日本語を含むか)、
公開されているベンチマーク数値、公開先 (arXiv / GitHub / Hugging Face)。

公式のリリース告知だけでなく、実際に試した人の評価も拾ってください。日本語での
精度、推論速度、動かすまでに詰まった点などの使用感は、公称値では分からない
判断材料になります。その際、公称のベンチマーク数値なのか個人の使用感なのかが
レポート上で区別できるように書いてください。

除外するのは、発信元による宣伝ポストと、モデル名に触れているだけで中身のない
言及です。批判的な意見や不満は除外しないでください。

レポートはモデル/手法ごとに整理し、日本語で使えるものを先に挙げてください。
```

## トラブルシューティング

- HTTP 401/403: `XAI_API_KEY` を確認。403 でクレジット切れの可能性
  (console.x.ai で残高確認)
- 出力が JSON でない / スキーマ不一致: `--raw-out` の生レスポンスを確認。
  structured outputs は Grok 4 系のみ対応
- 引用が少ない / 空振り: 期間を広げる、ハンドル指定を外す、プロンプトの検索語を
  増やす (英日両方、略語と正式名称の両方)
