# Google developer documentation style (日本語)

日本語のドキュメントを、Google developer documentation style guide の言語非依存の原則と下記の日本語表記規則に従って書く・修正する。理由を聞かれたら規則の slug(日本語表記規則は番号)で答える。原文ページは `https://developers.google.com/style/<slug>`(例外: index.md)。

前提:

- 優先順位: 1. プロジェクト固有のスタイル → 2. このガイド → 3. その他の参考資料。
- これはガイドラインでありルールではない。読者のためになるなら逸脱してよいが、文書内では一貫させる。
- **[Android]** / **[Cloud]** / **[Workspace]** の印がある規則はその製品のドキュメントにのみ適用する。対象が不明なら黙って適用せず確認する。
- 英語固有の規則(冠詞、sentence case、セリアルカンマ、ハイフネーションなど)は日本語本文に適用しない。文中の英語の UI ラベル・コード・コマンドには style-en の規則を適用する。

## コア規則(言語非依存)

### 声とトーン

- 会話調で親しみやすく、しかし軽薄にしない。俗語・バズワード・ネットスラングを使わない。
- 読者に直接語りかけ、手順は指示形で書く。「ユーザー」は読者が作るソフトウェアの利用者を指すときだけ使う。
- 能動態を基本とし、動作の主体を明確にする。現在形で書く。将来の機能やリリースを予告しない。
- 手順で「簡単に」「単に」「すぐに」など難易度を決めつける語を使わない。注意を引くだけの埋め草(「ご注意ください」)を書かない。
- ソフトウェアを人格化しない(「教えてくれる」ではなく「指定する」)。
- 条件・場所・目的を動作より先に書く(「ドキュメントを削除するには、**削除** をクリックします」)。
- 検証不能な性能・コストの主張、最上級表現、絶対的なセキュリティ主張をしない(「安全です」ではなく「セキュリティの向上に役立ちます」)。
- タイムレスに書く: 「現在」「近日中に」「最新の」「新しい」を避ける(例外: ブログ、リリースノート)。
- アクセシビリティ: 「上記」「下記」「右側」などの方向依存の表現を避け、「前述の」「次の」を使う。UI 要素はラベル名で参照し、色・大きさ・位置だけを手がかりにしない。
- インクルーシブ: 性別を仮定する表現、障害・暴力に由来する比喩、社会的に問題のある用語を避ける。慣用句を避け平易な語で書く。

### 構造と書式

- 順序があるなら番号付きリスト、なければ箇条書き、用語と説明の組は説明リスト。項目の構造を揃える。
- リスト・表・手順・コードは完結した導入文で導入する(項目が文の続きになる書き方をしない)。
- 見出し: タスクの見出しは動作(⭕ 「インスタンスを作成する」)、概念の見出しは名詞句(⭕ 「インスタンスのライフサイクル」)。ページ内で階層を飛ばさない。見出しにリンクや裸のコードを入れない。
- 手順: 1 ステップ 1 アクション。場所→操作の順。メニューの連続選択は「**File > New > Document**」の形にまとめる。任意の手順は「省略可:」で始める。
- 太字は UI 要素名のみ。コード・ファイル名・コマンドはコードフォント。強調のための太字・下線を使わない。
- プレースホルダは UPPER_SNAKE_CASE で書き、初出で説明する。
- 注記(Note/Caution/Warning)は控えめに使い、入れ子にしない。
- リンクテキストはリンク先の内容を表す語句にする(「こちら」「ここをクリック」や裸の URL を使わない)。
- すべての画像に代替テキストを付ける。情報を画像だけで提示しない。テキストやコードをスクリーンショットにしない。
- 例示の値は予約済みのドメイン・名前・IP・電話番号だけを使う(→ example-values.md)。実在の個人情報を使わない。

## 日本語表記規則

1. **固有名詞・製品名は英語表記のまま**: ⭕ Android ❌ アンドロイド。公式の大文字小文字に従う。
2. **定着した訳語・カタカナ語がある一般語は日本語で書く**: ⭕ オブザーバビリティ ❌ Observability。
3. **英数字・丸カッコ・引用符などの記号は半角**(句読点・かぎ括弧・中黒は全角のまま): ⭕ GKE (Google Kubernetes Engine) ❌ GKE(Google Kubernetes Engine)。
4. **和文と英数字の間に半角スペースを入れる**: ⭕ 「Cloud Run にデプロイする」 ❌ 「Cloud Runにデプロイする」。句読点・カッコ類と英数字の間には入れない(⭕ 「GKE を使う。」)。
5. **カタカナ語の長音記号は付ける**: ⭕ サーバー、ユーザー、コンピューター ❌ サーバ、ユーザ。
6. **句読点は「、」「。」を使う**: 「,」「.」を和文に使わない。
7. **感嘆符を避ける**: 本文・手順では使わない(コードや出力のリテラルは除く)。

8. **文体は敬体(ですます調)で統一する**: 既存文書が常体(である調)ならそれに合わせ、1 文書内で混在させない。

いずれも文書内・プロジェクト内の既存の規約が優先。規則 1・2 の境界(デプロイ/deploy などの定着度)はプロジェクトの用語集→既存文書の表記の順で判断し、どちらもなければ確認する。

## ワークフロー

- **修正**: コア規則と日本語表記規則で全体を走査する。手順・表・リンク・コマンドなど構造要素があれば、対応する style-en の参照ファイルを読んでから直す。
- **執筆**: 最初からコア規則を適用し、含まれる要素に対応する参照ファイルを先に読む。
- **説明**: 変更理由を聞かれたら規則名と slug(日本語表記規則はこの SKILL.md)を挙げる。
